## 0. Design principles that cut across every section

1. **One executor per request.** Exactly one code path may send a given upstream request at a given time. The HubDO
   leases each due job (compare-and-set, §1.4), so a mode switch, a duplicate alarm or a cron fallback can never send
   the same request twice (fixes code-scout H3).
2. **The Free plan's binding resource is rows written, then duration; not CPU or requests** (platform scout §3). Every
   design choice below is priced in rows written per day, and a test pins the per-poll write count (§6 T-ROWS).
3. **Measure the platform ourselves.** The Hub counts its own rows read/written, RPCs, alarms, WebSocket connects and
   active wall time (its own and the PollerDO's) and serves them at `GET /api/v1/ops` (§1.7). Counters are persisted
   in the same call that changes them (an idle Hub hibernates after 10 s and loses memory, so in-memory counters would
   lose most counts: F1). The dashboard (D-057) is the cross-check, not the instrument.
4. **Fail closed, as in Phase 1.** A source whose poller stopped shows "stale" within 2x the cadence in force (also
   right after a cadence shortens, §3.4); a page that lost its socket, or whose poller stopped, does not say "Live"; a
   calendar that is itself stale is "unknown" and never slows polling or hides staleness; the calendar never slows the
   endpoints that would correct it (§3.3 "feeders").
5. **Calendar facts come from the record, ranked and labeled.** A chamber's "in recess until <date>" names its basis
   (Speaker's designation in the Clerk's floor record; the Senate press gallery's log, unofficial; the Senate's
   tentative schedule). A label never outranks health: "stale" and "error" always win over "in recess".
6. **Every go-live step is one small push behind a switch.** Kill switches are wrangler `vars` (§5.4); rollback is a
   one-line forward commit, never a version rollback across a Durable Object migration. A bug in the shared new code is
   covered by a pre-built, pre-tested "revert kit" (§5.4), not by the switches.

## 1. Architecture

### 1.1 The shape (supersedes the "hot/warm PollerDO" picture in docs/ARCHITECTURE.md)

```
 supervisor cron (* * * * *, acts every 5th minute) ──ensure()──► PollerDO "main" (alarm on a 60-s grid)
                                                                   │  per alarm: hub.claimDue() → fetch (hosts in
                                                                   │  parallel, ≤ 4; one in flight per host) →
                                                                   │  hash → parse (≤ 1 per alarm) → hub.record()
                                                                   ▼
                                    HubDO "hub": store, poll_state (leases, budgets, targets), calendar facts,
                                    status, ledger, ops counters ──► hibernating WebSockets (/api/v1/live)
                                                                 ──► /api/v1/events, /status, /feed.json, /votes, /ops
```

**One PollerDO instance, not one per host and not hot + warm.** Reasons, each from the evidence:

| option | D-038 one-in-flight per host | duration (13,000 GB-s/day) | DO requests | verdict |
|---|---|---|---|---|
| per source | breaks: clerk.house.gov serves votes + floor, www.senate.gov serves LIS votes + schedule (code H2) | 7 objects waking | 7x alarms | no |
| hot + warm tiers (ARCHITECTURE) | breaks the same way when a host's endpoints sit in both tiers | 2 objects | 2x | no |
| per host (5) | holds per object, but a host's chain is the only thing serialising it; cross-host leases and budgets still need the Hub | 5 wakes per minute; an object "idle and eligible for hibernation [is] not billed for duration, even before the runtime has hibernated" it (F-quote, pricing page 2026-09-30), so duration is not the reason | 5x alarms, 5x claim/record RPCs | no |
| **one, hosts in parallel inside the alarm** | holds: inside one invocation each host is a serial chain (today's `poll.ts` grouping) | 1 wake per minute, active time measured by `/ops` `poller_active_ms` | 1x | **yes** |

The reason for one poller is D-038 (one in flight per host, one count-before-send authority) and 5x fewer DO
requests, not duration (F7). Whether a pending `AbortSignal.timeout(15 s)` (`poll.ts:209`) keeps the poller
non-eligible, and so billed, for up to 15 s after an alarm is unmeasured; `/ops` reports `poller_active_ms` and the
D-057/O3 dashboard GB-s cross-checks it.

The runner is keyed by a shard table `POLLER_SHARDS = { main: [every host] }`. A second shard (e.g. a sub-minute "hot"
shard for the vote entry points in Phase 3) is a one-line change plus its own decision row; it is not built now.

**No cadence goes below 60 s in P2.2** (the `types.ts:91` floor stays). The alarms fix timing (cron entered 29-124 s
late in the probe; alarms median 4 ms, max 89 ms, n=48), not cadence. Price of a 20-s tier for the two vote entry
points (House index, Senate menu) in business hours, for the Phase 3 decision: +3,840 polls/day x 2 rows + 1,920 extra
grid alarms ≈ +9.6k rows written/day and ≈ +7.7k DO requests/day (arith.), and the House index alone at 180 req/h; it
needs the P3.6 latency harness to show upstream changes faster than 60 s first.

### 1.2 The poll grid (replaces CRON_SLACK_S; fixes code H1)

- Each endpoint (and each dynamic target) is due on a grid of whole minutes: `due(n) = anchor + n x cadence_in_force`,
  where `anchor` = the next whole minute after the endpoint's first claim plus a stagger `60 s x
  (fnv1a(source|endpoint|target) mod (cadence/60))`. 60-s endpoints therefore all fall in the same minute (one alarm
  serves every host); hourly targets (10 House rolls) spread over the hour instead of bursting at :00.
- **Jittered phase (T12).** The alarm for grid minute `m` fires at `m + φ`, with `φ` drawn uniformly from [15 s, 45 s]
  each minute (not a fixed second). A fixed phase would phase-lock to Public Inspection's slot times (08:45:00 etc.): if
  the upload lands just after the poll's second, every slot is detected ~60 s late, every time. A random phase keeps
  Phase 1's property (the late cron effectively polled at a random second): expected detection delay ≈ 30 s whatever the
  upload lag. Consecutive 60-s polls are 30-90 s apart, inside the 120-s threshold. Test (`runner.test.ts`): over 1,000
  simulated minutes, no second-of-minute holds > 5% of 60-s polls, and no gap between consecutive 60-s polls exceeds
  90 s plus alarm lateness. One phase for all endpoints keeps one alarm per minute (a phase per endpoint would add an
  alarm + claim + record per extra phase, ≈ 4.3k DO requests/day each, arith.).
- **Heartbeat floor (F2, C9, T8).** The alarm is set to `min(earliest due + φ, now + 60 s)`: earliest over all jobs and
  backoff ends (a job in backoff is due at the first grid point at or after `backoff_until_ms`). So the poller wakes at
  least once a minute even when nothing is due (wh.feeds in backoff at night, every endpoint at 300 s+), and every
  wake calls `claimDue`, which stamps `poller_alarm_ms` and pushes a status message (§2.2). §1.6 already priced 1.44k
  grid alarms/day; the floor adds almost nothing. `claimDue` takes every job due at or before `now + 2 s`.
- A late alarm (documented failover delay up to 60 s) polls late; it never polls twice: a job is due only when
  `last_claim_ms < due point`, and claims are recorded before sending.
- `peakRequestsPerHour` becomes exact on a grid: fixed endpoint `ceil(3600 / min cadence)`; dynamic endpoint
  `maxTargets x ceil(3600 / cadence)` + leftovers (§4.3: at most `maxTargets`, polled no faster than 300 s) +
  `maxNewPerHour` (a new field: new targets are due at the next alarm, which is at most 60 s away). The `min(60, …)`
  cron cap is deleted with its tests (`policy.test.ts:70-88`, `poll.test.ts:548`).
- **Per-host cap (F5, T2).** `claimDue` returns at most `MAX_JOBS_PER_HOST = 6` jobs per host per alarm, oldest due
  first, except that a host's fixed endpoints (the entry points: House index, Senate menu, feeds) always come before
  its dynamic targets, so a burst of new targets never delays an entry-point poll (T-BUDGET's vote-a-rama case); the
  rest stay due for the next alarm (≤ 60 s later). A busy in-session minute on clerk.house.gov is 5 jobs (index, day,
  roll_next, and every 5th minute feed + next_day), so the cap bites only on bursts (deploy re-fetch, 10 rolls first
  listed at G8, ≈ 15 jobs), which drain in ≤ 3 alarms. 6 x 5 hosts = 30 fetches stays under the 50-subrequest limit
  with the Hub RPCs. Budgets are unchanged by this (it delays, never adds requests).

### 1.3 One alarm, step by step (`workers/api/src/poller_do.ts`, `runner.ts`)

1. `alarm()` wraps everything in try/catch and never throws (a throw costs up to 6 runtime retries and then the alarm
   is gone). It re-arms in `finally` with the `next_due_ms` the Hub returned, else `now + 60 s`.
2. `hub.claimDue({shard, now_ms, mode, alarm_started_ms})` → `{ jobs, next_due_ms, calendar }`. In one transaction
   the Hub stamps `poller_alarm_ms` (the poller heartbeat, §2.2), picks the due jobs of the shard's hosts (per-host cap,
   §1.2), skips those over budget (detail "hourly budget reached") or in backoff, and for each picked job writes ONE
   row: `poll_state` lease, `last_claim_ms`, `cadence_s_at_claim` (the cadence in force, §3.4), and the hour's request
   count (budget columns live in the same row: no separate `budget` row write). `lease_until_ms = now + 90 s`, which
   now bounds the real chain: a host's chain ends within its 20-s budget plus one 15-s timeout (step 3), and a queued
   parse gets its lease extended at step 4 (F5). A job already
   leased is not returned (CAS). A job whose lease expired while `parse_attempts ≥ 2` for the same `pending_body_key`
   is not returned: the Hub records drift "parse did not finish" for it and backs off (T7). Each job carries its URL
   (target URL for dynamic endpoints), the validator it may send, and the stored body key. If `claimDue` fails, nothing
   is sent this alarm (D-038). Every claimDue (even with zero jobs) ends with a status push to open sockets (§2.2).
3. Hosts run in parallel, at most 4 at once (the Free plan allows 6 simultaneous outbound connections per invocation;
   Hub RPCs need room). Within a host, requests are serial. **Per-host time budget (T2):** a host's chain stops at its
   first timeout or after 20 s of cumulative wall time; its unsent jobs go back in the quiet batch as `not_sent`
   (lease cleared, the hour's count refunded, no backoff, due again at the next alarm). So one hanging host delays the
   alarm by ≤ ~20 s plus one 15-s timeout, never 15 x 15 s, and other sources keep their grid. Per request: today's
   `fetchAndParse` rules unchanged (UA, validators, cache-buster, 15-s timeout, `cache: no-store`, body key = sha-256 +
   day tag + code version).
4. **Record the quiet results first** (T7): once every host chain has finished, the runner sends ONE
   `hub.record(batch)` with all quiet results (not_modified, error, not_yet, not_sent, drift before parse) BEFORE any
   parse, so a parse that later dies on CPU or memory cannot take other sources' results with it. Each changed body
   is then marked in the same call (`pending_body_key`, `parse_attempts + 1`: one row each, ≈ 1k rows/day, arith.).
5. **Parses: at most `MAX_PARSES_PER_ALARM` (= 1 until the D-057 readings and §6 T-CPU say otherwise) per invocation**,
   first-in-first-out. Further changed bodies wait in memory in a FIFO queue; the alarm is re-set to `now + 100 ms`, and
   a wake that finds a non-empty queue drains it (one parse each) BEFORE it claims anything new. If the object is
   evicted in between, the job's lease expires and it is fetched again at the next alarm (the request was counted;
   `parse_attempts` survives in `poll_state`). All parsing runs in the PollerDO, never in `scheduled()` (F3).
6. `notYetStatus` (H7): the exact status on that endpoint → outcome `not_yet` (health `empty`, "not posted yet", counts
   as a success for staleness, no backoff, never parsed, does NOT count as "accepted" for the target-keep rule). A
   404 on a target that was accepted before is `error` as usual.
7. Each parsed payload goes to the Hub as its own `hub.record(batch)` call (its events, records, targets and calendar
   facts), so the Hub's heavier storing work runs in its own invocation. The quiet batch (step 4) marks a changed body's
   lease `now + 60 s` so a queued parse keeps its lease. Each record writes the job's `poll_state` row (1 row), clears
   the lease and `pending_body_key`. If a record call fails, the runner sends a plain error for that job (D-038); if that
   fails too, the lease expires and the job is due again (counted, so never a request storm).
8. The Hub answers each call with `next_due_ms` for the shard; the runner arms `min(that, now + 60 s)` (§1.2). The
   runner times the invocation from entry to exit and sends it as `poller_active_ms` on its last record call of the
   alarm (§1.7 ops).

**Cron mode** (`POLL_MODE = "cron"`, §5.4; F3, T3): `scheduled()` does NOT run the runner. It calls
`poller("main").runOnce(now)`, so every fetch and parse still runs inside the PollerDO (Durable Objects: 30 s CPU per
invocation, F-quote; a Worker cron on Free: 10 ms with only "some built-in flexibility" for infrequent overruns,
F-quote). `runOnce` claims and runs exactly as an alarm does, except that in cron mode the PollerDO never arms the 60-s
grid alarm; it arms only the 100-ms parse-queue alarm, and that alarm only drains the queue. So cron mode has the same
parse deferral and FIFO as alarm mode, and no parse is dropped. Phase 1's `pollOnce` becomes a thin wrapper over
`runOnce`, so there is one poll implementation. The leases make an overlap between the modes harmless. Tests:
cron mode with 3 changed bodies in one minute → all 3 accepted within 1 s (3 queue drains); alarm mode → the same.

### 1.4 What the cron still does (the supervisor)

The trigger stays `* * * * *` (so cron mode needs no trigger change, and cron edits take up to 15 min to propagate).
In cron mode `scheduled()` first calls `poller("main").runOnce(now)` (§1.3). In both modes it then returns at once
unless `minute % 5 == 0`; then it:
1. (alarm mode only) calls `poller("main").ensure(now)`: if `getAlarm()` is null, or older than `now - 120 s` (a stuck alarm), it sets
   `setAlarm(now)`. The cron is a watchdog, not a clock: cron lateness of up to ~2 min was measured.
2. calls `hub.housekeep(now)`: ledger prune (today's hourly rule), `ledger_stats` recompute, expiry of calendar facts,
   and the chunked schema-version rewrite of §4.6 (chunk size from T-CPU, starting at 50 rows per call).
3. logs one line only when something was repaired (Workers Logs Free: 200k events/day).
Cost: 2 DO requests per 5 min = 576/day.

Lost-alarm bound: a lost alarm is re-armed within 5 min + cron lateness (≤ ~7 min). Users see "stale" after 2x the
cadence regardless (fail-closed), because the Hub judges staleness from poll results, not from the alarm.

### 1.5 Failure and restart behaviour

| event | what happens | what the page shows |
|---|---|---|
| alarm handler overruns CPU or memory | quiet results were already recorded (§1.3 step 4); runtime retries (2-s backoff, ≤ 6); leases expire; after 2 unfinished parses of one body key the Hub records drift "parse did not finish" and backs that job off (T7); supervisor re-arms | that one source: drift chip, then backoff; others unaffected |
| deploy | every DO restarts; alarms persist; in-memory queued bodies are lost (re-fetched at the next alarm); the new version id drops validators once (today's rule: every endpoint and target re-fetched and re-parsed once, drained over ≤ 3 alarms by the per-host cap); "WebSocket connections are terminated automatically" on code updates (F-quote, lifecycle page) | socket reconnects with `since` (§2.4) |

| Hub down | `claimDue` fails, nothing sent; pages: HTTP 503, socket closed | "Live data unavailable" |
| one host hangs | its chain stops at its first 15-s timeout (per-host budget, §1.3 step 3); its unsent jobs return as `not_sent`; the alarm ends ≤ ~35 s after it started; the next alarm (only one `alarm()` runs at a time) keeps every other source on its grid | that host's sources late, then stale; fr.api / wh.feeds unaffected (pinned by `runner.test.ts`: clerk.house.gov hangs with 15 queued jobs → alarm ends < 40 s on a fake clock, wh.feeds claimed at its next grid point) |

### 1.7 HubDO changes for polling

- `poll_state` (new, replaces `source_state` for reads and writes): PK `(source_id, endpoint_id, target)`, `target`
  = '' for fixed endpoints (fixes H4); columns of `source_state` plus `last_claim_ms`, `lease_until_ms`,
  `hour_start_ms`, `hour_count`, `anchor_ms`, `cadence_s_at_claim`, `cadence_s_at_success` (the cadence in force when
  the last successful poll was claimed, §3.4), `pending_body_key`, `parse_attempts`. No secondary index (an index adds a row write per update).
  Writes are `UPDATE … WHERE` on existing rows (1 row) and `INSERT` only for a new job; never `INSERT OR REPLACE`.
- `poll_targets` (new): PK `(source_id, endpoint_id, url)`; `added_ms`, `accepted_ms`, `initial` (0/1),
  `delisted_ms`, `error_streak`. Rules in §4.3.
- `ledger_stats` (new): PK `source_id`; `at_ms`, `items_24h`, `median_latency_s`. Recomputed by housekeeping (every 5
  min) and when that source's ledger gained a row; read by status. Survives hibernation (the in-memory cache does not).
  Consequence for D-039: both `median_latency_s` and `items_24h` can be up to 5 min stale (a rolling 24-h count also
  drops rows that age out, which only a recompute sees: F8) (decision row R-9).
- **Ledger rows only for real first sightings (C6).** Today `storeOne` runs `INSERT OR IGNORE INTO ledger` for every
  incoming copy (`hub.ts:549-554`), and the ledger is pruned after 7 days (`hub.ts:141,451-453`). After a deploy
  (every target re-parsed once, `policy.ts:142-153`) a roll listed for > 7 days re-enters the ledger as a new sighting
  with a latency of weeks. New rule: a ledger row is written only when the event is new to the store (`prior == null`)
  or the stored copy does not yet cite this source. Test (`hub.test.ts`): a payload re-ingested 8 days after its first
  sighting (ledger pruned) writes no ledger row and leaves `median_latency_s` and `items_24h` unchanged.
- `ops` (new): ONE wide row per UTC day (PK `day`, one column per counter), updated with `UPDATE ops SET c = c + ?, …`
  inside the same transaction as each Hub call that changes a counter (1 row written per such call, ≈ 3.2-5k/day,
  §1.6). Nothing is held in memory, so hibernation loses nothing (F1). `GET /api/v1/ops` serves today's and yesterday's
  counters: hub_rows_written / rows_read (summed from `cursor.rowsWritten` / `rowsRead` of every `sql.exec`, the ops
  update included), rpc calls by method, alarms, set_alarm, ws_connects, ws_messages_in, broadcast_failures, storage
  bytes (`PRAGMA page_count`), `poller_active_ms` (the PollerDO's own entry-to-exit time per invocation, sent on its last
  record call) and `hub_active_ms` (the Hub's per-call wall time), the duration proxies §1.6 needs. Test
  (`ops.test.ts`, workerd): two calls separated by a forced Hub eviction both appear in the counters.
- Constructor (fixes H16): read `meta.schema_rev` first; when it equals the code's rev, run NO DDL. Only a new or older
  store runs `SCHEMA` and migrations (§5). The cursor epoch and seq are read as today.

## 2. The live channel: `/api/v1/live` over a hibernating WebSocket

### 2.1 Route and handshake

- Worker (`http.ts`): `GET /api/v1/live` with `Upgrade: websocket`, else 426 JSON. Origin must equal `PAGES_ORIGIN`
  (browsers do not apply CORS to WebSockets, code H11); a missing or other Origin gets 403 JSON. This keeps other web
  pages from embedding our socket; it does not stop a non-browser client, which is acceptable for public read-only
  data. A local-dev origin list exists only in `wrangler.e2e.jsonc` (§6), never in the production config.
- `LIVE = "off"` (§5.4): the route answers 503 JSON and `/api/v1/status` omits `transport.live`, so the page never
  tries the socket.
- The Worker forwards the request to the Hub with `stub.fetch(request)`. The Hub: if `ctx.getWebSockets('live').length
  >= LIVE_CAP`, it accepts and immediately closes with 1013 "try again later" (the client then polls every **60 s** for
  5 min, not 15 s: F4). `LIVE_CAP` is set from T-CPU's measured broadcast cost per socket so that one broadcast of a
  256-KB message to every socket stays under 1 s of CPU in workerd (start: 1,000; the platform allows 32,768
  hibernatable sockets per object, F-quote). A refused socket is the cheap path to protect: on a socket a tab costs
  ≈ 30 DO requests/day, while 15-s polling costs 11,520 Worker + 11,520 DO requests/day, so ≈ 9 polling tab-days use
  the whole Free day. Otherwise
  `ctx.acceptWebSocket(server, ['live'])`, `serializeAttachment({ connected_ms })`, and sends `hello` at once.
- Cost per connect: 1 Worker request + 1 DO request. Outgoing messages are free and do not wake billing beyond the send.

### 2.2 Messages (contract in `packages/schema/src/api.ts`, `LiveMessage`; events spliced as stored JSON text)

```ts
type LiveMessage =
  | { type: 'hello'; v: 1; generated_at: Utc; cursor: string; status: StatusResponse
      catchup: { from: string; events: CedEvent[]; has_more: boolean } | { reset: true } }
  | { type: 'events'; from: string; cursor: string; sent_at: Utc; events: CedEvent[] }
  | { type: 'status'; cursor: string; status: StatusResponse }
  | { type: 'gap'; cursor: string }
```

- `hello`: the client connects with `?since=<cursor>`. A valid cursor gets every change after it (the `/events?since`
  query, at most 200 events); an invalid one (another epoch, ahead, malformed) gets `{reset: true}` and the client
  re-snapshots over HTTP (D-040's 400 path).
- `events`: sent right after `recordPoll`'s transaction commits, with the rows written by `storeOne` in seq order;
  `from` is the cursor before them. A client applies it only when `from` equals its own cursor (continuity), else it
  treats the message as a gap. More than 200 events or 256 KB → a `gap` message instead (the client fetches
  `?since=` over HTTP, up to 10 pages as today). That is the whole backpressure story: the hibernation API exposes no
  per-socket buffer, so the server bounds message size and lets slow clients catch up over HTTP.
- `status`: the full StatusResponse (same contract and guards as `GET /status`), sent on every `claimDue` (at least
  once a minute, because the PollerDO wakes at least every 60 s whatever is due, §1.2: F2, C9, T8), and at once when
  a "material" field changes (health, stale, detail, error_streak, calendar, items_24h). It no longer depends on any one
  source polling every minute. Size ≈ 4-5 KB; ≤ ~7 MB/day for a page left open all day (arith.). Its `cursor` is the
  Hub's current cursor: a client outside CATCHING_UP whose own cursor differs treats it as a gap (C3).
- **Two liveness stamps (C9).** `StatusResponse.poller = { last_alarm_at: Utc | null }` (from `poller_alarm_ms`, kept
  in the ops day row, so no extra row write) proves the PollerDO is running; `generated_at` proves the Hub is. The page
  shows "Live" only while BOTH are within 150 s by the Hub's clock (`generated_at − last_alarm_at ≤ 150 s`) and the
  message arrived within 150 s by the client clock. A Hub that is alive while the poller is dead therefore never reads
  "Live" (the header reads "Updates paused: poller not running", and the per-source chips go stale as before).
- Client → server: nothing. A received message is answered with close 1003 (each incoming message is a billed DO
  request). The Hub's once-a-minute status also keeps Cloudflare's edge idle timer from closing the socket ("Cloudflare
  will close a WebSocket connection when no data is transmitted in either direction for a period of time", F-quote; a
  third-party write-up says 100 s on Free). If `/ops` or the e2e soak shows edge closes anyway, the fallback is
  `setWebSocketAutoResponse` ping/pong (does not wake the object; incoming messages billed 20:1, ≈ 72 DO requests per
  tab-day at one ping a minute, F-quote), its own decision row.
- Broadcast failure never fails `recordPoll` (H14): broadcast runs after the commit, in its own try/catch per socket,
  and counts `broadcast_failures` in ops.

### 2.3 Hibernation details

- The Hub hibernates after 10 s without events ("the in-memory state is discarded", F-quote, lifecycle page); the
  constructor then re-runs on the next RPC or poller call, so it must be cheap (§1.7 schema_rev). Nothing that must
  survive lives in memory (ops counters and ledger aggregates are persisted, §1.7). The "last status sent" hash lives in
  memory; after a wake the first call sends a status message (harmless; it is sent every minute anyway).
- `webSocketClose` / `webSocketError`: nothing to do (compat date 2026-10-01 ≥ 2026-04-07, the runtime replies to Close).
- The Hub never sets its own alarm for heartbeats; the PollerDO's ≥ once-a-minute `claimDue` is the heartbeat, and it
  also carries the poller's own liveness (§2.2).

### 2.4 The page's state machine (`apps/web/src/live.ts` + `store.ts`; extends D-040, never weakens it)

| state | entered when | shows | leaves when |
|---|---|---|---|
| BOOT | page load | "Loading…" (never "No events") | first HTTP poll commits → OPENING; fails → UNAVAILABLE |
| OPENING | a committed snapshot and `status.transport.live` present | header "Updated hh:mm:ss" | `hello` valid → LIVE; error/close/10-s timeout → POLLING |
| LIVE | `hello` committed and the poller stamp fresh | header dot "Live" + time of the last status message | silence > 150 s, a status older than 5 min by the client clock (D-040 rule), `poller.last_alarm_at` older than 150 s before `generated_at` (→ POLLING with "Updates paused: poller not running"), a `status.cursor` ≠ own cursor (→ CATCHING_UP), a malformed message, or close → see below |
| CATCHING_UP | `gap`, a `from` mismatch, a `status.cursor` mismatch, `has_more`, or `reset` | as LIVE but no dot | HTTP `?since=` pages commit, then the buffer is applied → LIVE; fail → POLLING |
| POLLING | socket unavailable (close, 1013, LIVE off, repeated failure) | Phase 1 behaviour: 15-s polls, "Updated hh:mm:ss"; after a 1013 (cap) 60-s polls for 5 min | reconnect succeeds → OPENING |
| UNAVAILABLE | any HTTP poll fails (D-040) | "Live data unavailable" banner with reason and last good time; last rows stay | next good poll |

- Commit rules (new decision row R-12, amends D-040 for the socket): a `hello` commits rows, status and cursor at once;
  an `events` message commits rows and cursor (it carries its own continuity check); a `status` message commits status
  only. Every message passes the same guards as HTTP answers (`lib/guards.ts`); a malformed message is a gap, never a
  partial apply. The 5-min `generated_at` rule applies to every status, HTTP or pushed.
- **No message is dropped during catch-up (C3).** In CATCHING_UP every `events` message is buffered (bounded: 50
  messages, else one more catch-up round). When the HTTP pages commit, buffered messages whose `from` equals the new
  cursor are applied in order and the rest are discarded (their rows were in the HTTP pages, or the next mismatch
  re-enters CATCHING_UP). And outside CATCHING_UP, any `status.cursor` ≠ the client's cursor is a gap, so a lost
  `events` message is caught within one status message (≤ ~60 s), not at the next event hours later. Both cases are in
  the failure-path e2e (§6 E2): an `events` message arriving mid-catch-up whose rows were committed after the HTTP query
  ran must appear; a dropped `events` message must be recovered within 70 s.
- "Live" is shown only in LIVE. An empty feed is shown only after a successful snapshot with zero events (D-040).
- Reconnect: delay `min(60 s, 1 s x 2^n)` with full jitter, reset after 5 min connected; immediate on `online` and on
  becoming visible. While reconnecting, POLLING runs, so data keeps arriving.
- Hidden tab: the socket stays open for 5 min hidden (costs nothing server-side), then closes; becoming visible
  reconnects with `since`. iOS may kill it sooner; the reconnect path covers that.
- Text changes: `app.tsx:85` "Retrying every 15 seconds" becomes state-specific ("Reconnecting…", "Retrying every 15
  seconds"); the header shows "Live" or "Updated hh:mm:ss".
- `apps/web/e2e/mock-api.ts` gains `page.routeWebSocket` so no test can reach a real `wss://` (H12); the network fence
  test asserts zero real WebSocket connections.

## 3. Calendar-aware staleness

### 3.1 What "calendar-aware" changes, and what it does not

Stale still means "no successful poll within the endpoint's threshold" (D-039/D-049). The calendar changes three
things only: (a) the cadence in force (recess, holidays, a sitting chamber at night); (b) through (a), the threshold;
(c) a label in the status ("in recess until Nov 9", "no Federal Register issue today (Columbus Day)"). Recess never
makes a poll fail, so (b) alone keeps a slowly-polled Congress source from flashing "stale"; (c) is what the Phase 2
exit asks the page to say.

### 3.2 Facts and their sources (ranked; one fact type per row)

endpoint's health detail ("calendar fact dropped: …"), and the payload's events are judged exactly as without it. This
holds whatever `CALENDAR` says (facts are stored but unused while it is off). Test (`hub.test.ts`): valid

### 3.3 Chamber state (pure: `workers/api/src/calendar.ts` `chamberState(facts, events, health, nowMs)`)

Terms. A **business day** is a `meeting_day` of kind `business`; a recorded roll call (from the chamber's vote
source) also makes its legislative day a business day. **Feeders** are the endpoints that detect sitting and calendar
facts: House `house.clerk.floor` (feed, day, next_day); Senate `senate.pressgallery` and `senate.schedule` `floor`.
The **sitting sensor** is House `house.clerk.floor` day/feed and Senate `senate.pressgallery` (the only Senate source of
convene/adjourn).

Evaluated in this order, per chamber:
1. **unknown** when the chamber's sitting sensor is stale or never succeeded (C8: for the Senate the gallery alone
   decides; a live schedule with a dead gallery cannot see the Senate sitting). Label none; cadence normal (Phase 1
   business/off rules). This is the fail-closed case. (The draft's "no fact younger than 14 days" clause is removed
   (C1): a recess fact is bounded by its own dates, and a dead sensor is caught here.)
2. **sitting** when (a) the most recent `meeting_day` **of any date** has a convene within the last 24 h and no
   finish/adjourn, and it is a business day or its convene is less than 1 h ago (a pro forma has no adjournment line,
   so it counts as sitting only for 1 h: C1); this covers a legislative day that runs past midnight (votes at 2:49 AM,
   roll2025_143: C4); or (b) a new roll call or `floor.convened` (business) event from the chamber's vote/floor sources
   arrived within the last 2 h (C8: an unscheduled return is "sitting" from its first record, whatever the facts say).
   Cadence: `business_s` whatever the clock. Label "in session".
3. **recess** when not sitting and a recess fact covers today (Eastern date):
   - House: `from ≤ today ≤ through` of the newest designation, unless a business day falls inside the period after
     `announced_at`: then the designation is void for the rest of its period (the 2025-11-12 case: the House returned
     for business inside a designated period; C10);
   - Senate: `today < return_for_business date`, the fact announced after the last business day (one definition,
     used in §3.2 and here: C1);
   - else a tentative `recess_period` covering today.
   A pro forma meeting neither ends a recess nor starts one. Cadence: `max(normal cadence in force, recess_s)` for
   non-feeder endpoints only (hearings' 3600-s off cadence is never sped up by a 900-s `recess_s`: decision R-14
   amends D-065), except within the meeting window `[next_meeting − 15 min, next_meeting + 2 h]`, where normal cadence
   applies (pro forma sessions get recorded). **Feeders never take `recess_s`** (C8): they keep their normal
   business/off cadence, so an unscheduled return is seen within one normal cadence (House day file 60 s by day, 300 s
   at night). This changes `house.clerk.floor`'s `calendar.recess_s` (3600) into an endpoint-level opt-out
   (`Endpoint.calendarFeeder: true` on feed/day/next_day; same for the gallery and `senate.schedule` `floor`), R-14.
4. **between_days** otherwise. Cadence: normal. Label: "next meeting <next_meeting_at>" when that fact exists, else
   none. **"in recess" is never printed without a recess fact (C10).**

The D-065 "next convene more than 24 h away" rule is replaced: it flips at every pro forma (the Senate would count as
not in recess for 286 of 886 h, calendar scout).

Unit tests (`calendar.test.ts`) add, beyond §6 E3: a pro forma convene with no adjournment → `sitting` for 59 min,
`recess` at 61 min; a business day convened 23:30 ET and not finished → `sitting` at 02:49 ET next day; a roll call
inside a designated period → House `between_days`/`sitting`, never "recess" for the rest of it; gallery stale and
schedule fresh → Senate `unknown`; a roll event during a designated period with the floor feed stale → `unknown` (rule 1
first).

### 3.4 Thresholds and the text

- **Threshold per endpoint (C7, T15).** Let `c(now)` be the cadence in force now, `cs` = `cadence_s_at_success` (the
  cadence in force when the last successful poll was claimed, stored in `poll_state`), and `t_c` = the time the current
  cadence came into force (the start of the current calendar state or business/off window; `calendar.ts` returns it
  with the state). The endpoint is stale when EITHER
  (a) `now − last_success > max(freshness_slo_s, 2 x max(cs, c(now)))`, OR
  (b) `c(now) < cs` and `now − max(last_success, t_c) > 2 x c(now)`.
  (a) is the steady-state rule (an hourly recess poll gives 7,200 s; a state flip to `unknown` that shortens the
  cadence does not flash "stale" for a healthy endpoint, because the last success was under the recorded slower
  cadence). (b) is the fail-closed rule when the cadence shortens: once the meeting window opens or the chamber starts
  sitting, a poller that died stays "ok" for at most 2 x the new cadence (2 min for a vote entry point), not an hour.
  This replaces the draft's "slowest cadence over the last M" rule, which derived past cadences from current facts.
- `SourceStatus.calendar?: { scope: 'house' | 'senate' | 'fr'; state: 'sitting' | 'recess' | 'between_days' |
  'no_issue' | 'issue_day' | 'unknown'; until_date: string | null; through_date: string | null; next_meeting_at: Utc |
  null; basis: string | null; holiday: string | null }` (optional, additive; absent when `CALENDAR = "off"`). Structured
  fields only; the page builds the words (C11: times in the viewer's zone, D-041; dates are Eastern calendar dates and
  shown as dates). Guards accept its absence. Also `SourceStatus.current_keys?: string[]` for endpoints that emit
  `scheduled_convene` rows: the convene keys in the source's latest accepted payload (≤ 20), used by the D-083 chip
  (§4.5, C12).
- Text the page builds (C10, C5):
  - House, designation: "in recess through Nov 8 · Speaker's designation". The Clerk states only "through Sunday,
    November 8"; no source says the House returns Nov 9, so the House never reads "until" (owner question O4 asks
    whether this wording satisfies the exit's "in recess until Nov 9"; default yes, see §9).
  - Senate, return fact: "in recess until Nov 9 · press gallery log (unofficial)". The basis is visible text after a
    middle dot, never a tooltip (iPhone Safari has no hover: C5).
  - Senate, tentative period only: "in recess through Nov 6 · tentative schedule"; never a derived Monday.
  - between_days with a next meeting: "next meeting Mon Oct 5, 4:00 PM EDT" (viewer's zone), never "in recess".
- Page chip precedence (amends D-041): never_polled > error with no success > **stale** > error/drift > **calendar
  label** (state recess or no_issue) > ok. So "in recess until Nov 9" replaces only "ok"; a dead poller in recess still
  reads "stale".

## 5. HubDO SQLite migration plan

### 5.1 Rules

- Migrations are additive: `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ADD COLUMN`, `INSERT … SELECT` copies. No
  `DROP`, no destructive `UPDATE` of facts. The only content rewrite is §4.6's `schema_version` (not a fact).
- Each rev runs in one `transactionSync` inside `blockConcurrencyWhile`, and bumps `meta.schema_rev` in the same
  transaction. A failed migration rolls back whole; the Hub then answers 503 (fail closed) and the next wake retries.
- The epoch and seq never change, so every client cursor and `scripts/ledger_report.mjs` keep working (a store reset
  makes every cursor answer 400, TRAPS).

### 5.2 Revisions

| rev | push | DDL / copy | rows written once (arith.) |
|---|---|---|---|
| 1 | (today) | tables of `SCHEMA` + `events.checked` | — |
| 2 | G1 | `poll_state` + `INSERT INTO poll_state SELECT …, '' AS target … FROM source_state`; `poll_targets`; `ledger_stats`; `ops`; `calendar_facts`; `member_votes` (empty). Worker config: migration `{ "tag": "v2", "new_sqlite_classes": ["PollerDO"] }` in the existing legacy `migrations` array (Free allows only SQLite-backed DOs; new key-value classes are "no longer supported", and a Worker may use only one migrations flow: F6) | ≈ 5 |
| 3 | G9 | none (the "0.1" rewrite runs in housekeeping chunks, §4.6) | ≈ events count, spread |
| 4 | ≥ 30 days after G2 | `DROP TABLE source_state` and `budget` (own decision row; only after the cron-mode fallback has used `poll_state` for a month) | — |

`source_state` and `budget` are left untouched and unread from G1 to rev 4. That alone does NOT make the Phase 1 code
runnable again (T4): a plain `git revert` of G1 drops the `PollerDO` export while the `v2` migration and its object
exist, which Cloudflare refuses to deploy (a class with live objects must stay exported or be deleted by a migration),
and Phase 1 code would read `source_state` frozen at its G1 contents. The tested way back is the revert kit (§5.4).

### 5.3 Backup and checks before G1

- `scripts/export_store.mjs` (new, read-only, public API): pages `GET /api/v1/events?since=<epoch>.0&limit=500` until
  `has_more` is false (every current row, oldest change first) and saves JSONL + `/api/v1/status` + `/api/v1/ops`
  outside the repo, with sha-256 and counts in PROGRESS. It is evidence of what existed, not a restore path (there is no
  import endpoint before Phase 3's ingest), so the no-data-loss guarantee rests on §5.1.
- `workers/api/test/migrate.test.ts`: builds a rev-1 store with today's DDL and rows taken from that export (a
  committed sample, ~200 rows), runs the new constructor, and asserts: same epoch and seq; every `/events?since=`
  answer byte-identical; status identical except the new optional fields; poll_state equals source_state row for row;
  and a second constructor runs zero DDL statements (counted via a spied `sql.exec`).
- Rollback-compatibility test: today's `SCHEMA` statements and `plan()` / `status()` queries run unchanged against a
  rev-2 store.

### 5.4 Rollback

- **Never a version rollback** across the `v2` Durable Object migration (Cloudflare documents rollbacks as unsupported
  across DO migrations; the build session re-reads that page before G1 and records the quote). Rollback = a one-line
  forward commit flipping a `vars` switch, through the normal gate (~5 min):

| switch | values | off-state behaviour |
|---|---|---|
| `POLL_MODE` | alarms / cron | the cron calls `PollerDO.runOnce()` once a minute (all fetching and parsing stay in the DO, §1.3); the grid alarm re-arms itself never (each alarm checks the mode first; only the parse-queue alarm runs) |
| `LIVE` | on / off | `/live` 503, status omits `transport.live`, pages poll every 15 s |
| `CALENDAR` | on / off | Phase 1 cadences (weekdays 06-22 ET), no labels |

- **Switch typing and test coverage (T6).** `wrangler types` writes `vars` as literal types (`worker-configuration.d.ts`
  today: `PAGES_ORIGIN: "https://…"`), so `env.POLL_MODE === 'alarms'` would be a TS2367 error while the config says
  "cron". Switches are read only through `switches.ts` `readSwitches(env: { POLL_MODE?: string; … })`, typed `string`,
  with unknown values failing closed to the Phase 1-like state (cron / off / off) and a logged line. `workers/api`
  gets a second vitest project (`api-alarms`) with `miniflare.bindings` = alarms / on / on, beside the default project
  that reads `wrangler.jsonc`; a gate check asserts both projects ran a non-zero test count. So each mode's DO paths
  run in workerd whatever the production config says. The Playwright fail-closed suite (mocked API) runs once; its
  "both modes" claim is dropped: the mocked API has no modes.
- **Revert kit (T4), built and gated at G0 (before any P2.2 push):** a branch `p2.2-revert-kit` = the Phase 1 code
  plus (a) the `v2` migration entry, (b) a stub `PollerDO` class whose `alarm()` and `runOnce()` delete the alarm and
  return, exported beside `HubDO`, and (c) a Hub constructor that, when it finds `meta.schema_rev ≥ 2`, copies
  `poll_state`'s `target = ''` rows back into `source_state` (validators, last success, backoff) once, so the Phase 1
  poller resumes from current state instead of G1's frozen rows. Tested in workerd against a rev-2 store built by
  `migrate.test.ts`: the deploy shape is accepted by `wrangler deploy --dry-run`, `/events?since=` answers are
  byte-identical, the cursor epoch is unchanged, and the first cron poll sends validators from `poll_state`. The kit
  is re-based and re-tested at each G-step that changes the Hub's stored shape (only G1 and G9 do). Using it is a
  forward push through the gate like any other.
- A Congress source rollback removes it from `SOURCES` (its state rows stay; status stops listing it).
- The PollerDO class is never deleted (a `deleted_classes` migration would be irreversible); a dormant class costs
  nothing.
